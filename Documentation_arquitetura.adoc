== Identificação dos requisitos
Para a identificação dos requisitos foram utilizadas suas devidas categorias, usando uma abreviação da mesma, como por 
exemplo:

 * *RF* - Requisitos Funcionais

 * *RNF* - Requisitos Não Funcionais

Já para identificar suas o número a qual tal funcionalidade pertence, foi utilizado um sistema numérico onde cada casa numérica representa algo, como no exemplo:

*RF001*

* *Primeira casa decimal:* representa a camada a qual a funcionalidade pertence, exemplo: segurança, apresentação

* *Segunda casa decimal:* representa a categoria de atores que a usam, exemplo: usuario, visitante, admin

* *Terceira casa decimal:* representa a instância específica da funcionalidade, exemplo: cadastro, edição, exclusão

== Descrição geral do sistema

O sistema FairTech Vote e um sistema que procura facilitar a votação em feiras de ciências, o mesmo será
desenvolvido com a ideia de uma aplicação web API em uma intranet conectada a uma aplicação terminal por meio 
de totens, em termos de arquitetura o sistema está sendo planejado por meio de microserviços usando duas apis principais
uma responsavel pelo armazenamento de dados da feira tais como projetos e eventos tendo como foco a rápida leitura
dos mesmos e outra responsavel pela coleta e processamento dos votos, garantindo a integridade e segurança das informações, para isso será utilizado dois banco o couchbase agira na recuperação de dados com alta demanda de escrita como os votos e o cassandradb sera utilizado para consultas mais complexas e com alta demanda de leitura, tais como a apresentação dos projetos.

=== Descrição dos Usuarios

Os usuários que estão sendo projetados para o sistema FairTech Vote estão classificados em:

* *Visitantes:* Usuários que tem acesso a visualização de projetos e eventos, podendo votar nos projetos apresentados.

* *Organizadores:* Usuários responsáveis pela criação e gerenciamento dos eventos e projetos, podendo visualizar estatísticas de participação e votação.

=== Requisitos Funcionais:

* *[RF001] - Cadastro de Organizador:*
O sistema deve permitir o armazenamento de dados dos organizadores para gerenciamento dos eventos e projetos.
** *Ator:* Organizador
** *Prioridade:* Backbone
** *Entradas e pré-condições:* Para o organizador ser registrado o mesmo deve pertencer a uma instituição de ensino, 
previamente cadastrada e entrar com dados tais como nome, email para caso seja necessário recuperar senha, senha para
controle de acesso e instituição para determinar qual instituição o organizador está representando lembrando que o mesmo
poderá agir em mais de uma instituição.
** *Saídas e pós-condições:* No caso de o cadastro ser bem sucedido uma mensagem de sucesso deve ser retornada, em caso de negativa, uma mensagem de falha deve ser apresentado, e um registro da tentativa nos arquivos de log, junto ao motivo da falha.

* *[RF002] - Entrada do organizador:*
A entrada do organizador será por meio de uma interface web ligada por meio de intranet ao totens
** *Ator:* Organizador
** *Prioridade:* Backbone
** *Entradas e pré-condições:* O organizador entrará no sistema usando seu email e senha, previamente cadastrados.
** *Saídas e pós-condições:* Caso confirmado que a senha e usuario são validos um token  de acesso para o mesmo deve ser gerado, e o usuario será redirecionado para a página principal do sistema.

* *[RF003] - Recuperação de senha para o organizador:*
O sistema permitira a recuperação de conta com base em dados que o organizador forneceu durante o cadastro.
** *Ator:* Organizador
** *Prioridade:* Backbone
** *Entradas e pré-condições:* Na recuperação de conta o ator deve fornecer seu cpf e a instituição que o mesmo representa.
** *Saídas e pós-condições:* Caso a busca com os dados cedidos sejam válidos, um link para redefinição de senha deve ser enviado para o email cadastrado.

* *[RF100] - Cadastro do Evento:*
O evento deve ser cadastrado dentro do sistema para associação de projetos e visitantes.
** *Ator:* Organizador
** *Prioridade:* Backbone
** *Entradas e pré-condições:* Para o cadastro do evento, deve ser fornecido um nome, descrição, data de início e data de término,local do evento.
** *Saídas e pós-condições:* Caso o cadastro de evento seja bem-sucedido, um mensagem de sucesso deve ser apresentada e um registo do evento e do usuario que realizou o cadastro do mesmo deve ser armazenado, caso não um registro sobre a tentativa e o motivo da falha deve ser gravado nos artigos de log.

* *[RF101] - Edição de evento:*
Deve ser permitido a alteração de dados do evento antes do mesmo entrar em atividade, durante a atividade e após a atividade não deve mais ser permitido edições do mesmo.
** *Ator:* Organizador
** *Prioridade:* Backbone
** *Entradas e pré-condições:* Para a edição do evento, deve ser apresentado o identificador do evento assim como os dados a serem editados, de um evento previamente cadastrado.
** *Saídas e pós-condições:* Caso a edição seja bem-sucedida, uma mensagem de sucesso deve ser retornado e um registro de edição deve ser armazenado com o coordenador que fez a alteração assim como caso não, uma mensagem de falha deve ser apresentada e um registro com o motivo da falha registrado.

* *[RF102] - Abertura do evento:*
Por meio de crownjobs ou meios de agendamento o sistema deve ser capaz de abrir o evento na data e hora programadas, permitindo que o sistema de votação inicie e que o evento deixe de ser editável para os coordenadores.
** *Ator:* Sistema
** *Prioridade:* Core
** *Entradas e pré-condições:* Para a abertura do evento, deve ser apresentado o identificador do evento e a data e hora programadas para a abertura.
** *Saídas e pós-condições:* Caso a abertura do evento seja bem-sucedida, uma mensagem de sucesso deve ser retornada e um registro de abertura deve ser armazenado com o sistema que fez a alteração, assim como caso não, uma mensagem de falha deve ser apresentada e um registro com o motivo da falha registrado.

* *[RF103] - Encerramento do evento:*
Após o tempo limite do evento acontecer e o sistema de contagem de pontos ser iniciado o sistema deve ser capaz de registrar o vencedor e encerrar o evento.
** *Ator:* Sistema
** *Prioridade:* Core
** *Entradas e pré-condições:* Para o encerramento do evento, deve ser apresentado um sinal vindo do sistema de contagem de pontos.
** *Saídas e pós-condições:* Caso o encerramento do evento seja bem-sucedido, uma mensagem de sucesso deve ser retornada e um registro de encerramento deve ser armazenado com o sistema que fez a alteração, assim como caso não, uma mensagem de falha deve ser apresentada e um registro com o motivo da falha registrado.

* *[RF104] - Contagem de pontos:*
O sistema deve ser capaz de contar os pontos dos participantes durante o evento.
** *Ator:* Coordenador
** *Prioridade:* Backbone
** *Entradas e pré-condições:* Para a contagem de pontos, deve ser apresentado o identificador do evento.
** *Saídas e pós-condições:* Caso a contagem de pontos seja bem-sucedida, o projeto vencedor deve ser apresentado em uma mensagem, caso apresente algum erro uma mensagem de error deve ser enviada ao administrador para reparos.

* *[RF110] - Registro de Projeto:*
Projetos devem ser cadastrados associados a um evento especifico.
** *Ator:* Organizador
** *Prioridade:* Backbone
** *Entradas e pré-condições:* Para o cadastro do projeto, deve ser apresentados dados como nome, descrição, localização, e o evento ao qual o mesmo pertence.
** *Saídas e pós-condições:* Caso o cadastro do projeto seja bem-sucedido, uma mensagem de sucesso deve ser apresentada e um registro do projeto e do usuário que realizou o cadastro do mesmo deve ser armazenado, caso não um registro sobre a tentativa e o motivo da falha deve ser gravado nos artigos de log.

* *[RF111] - Edição do Projeto:*
O sistema deve permitir a edição dos dados de um projeto cadastrado.
** *Ator:* Organizador
** *Prioridade:* Backbone
** *Entradas e pré-condições:* Para a edição do projeto, deve ser apresentado o identificador do projeto assim como os dados a serem editados.
** *Saídas e pós-condições:* Caso a edição seja bem-sucedida, uma mensagem de sucesso deve ser retornada e um registro de edição deve ser armazenado com o coordenador que fez a alteração assim como caso não, uma mensagem de falha deve ser apresentada e um registro com o motivo da falha registrado.

* *[RF112] - Desqualificação do Projeto:*
O sistema deve permitir a desqualificação de um projeto cadastrado.
** *Ator:* Organizador
** *Prioridade:* Backbone
** *Entradas e pré-condições:* Para a desqualificação do projeto, deve ser apresentado o identificador do projeto.
** *Saídas e pós-condições:* Caso a desqualificação seja bem-sucedida, uma mensagem de sucesso deve ser retornada e um registro de desqualificação deve ser armazenado com o coordenador que fez a alteração assim como caso não, uma mensagem de falha deve ser apresentada e um registro com o motivo da falha registrado.

* *[RF011] - Cadastro do Visitante:*
O sistema deve possibilitar o visitante realizar seu cadastro para realização do voto
** *Ator:* Visitante
** *Prioridade:* Backbone
** *Entradas e pré-condições:* No cadastro do usuario e necessário informar o CPF, e opcionalmente o nome e email dados como senha são desnecessários porém o mesmo terá que fazer um cadastro do rosto para reconhecimento e associação ao cadastro.
** *Saídas e pós-condições:* Após o cadastro, caso bem sucedido o visitante receberá uma mensagem de sucesso, caso mal sucedido uma mensagem de erro deve ser apresentada, e um registro com o motivo da falha deve ser gravado nos artigos de log.
